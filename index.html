1. Introduction to File Processing

📌 Core Concepts

File Structure Definitions

  • File: A collection of records stored in secondary storage
  • Record: A collection of related fields
  • Field: The smallest logically meaningful unit of information
  • Key: A subset of fields used to identify the record
  • Primary Key: Uniquely identifies a record (e.g., ISBN, Student ID)
  • Secondary Key: Non-unique keys used for searching (e.g., Department, Class)

Logical vs Physical Files

  • Logical File: How programmers see the file (text, image, data file)
  • Physical File: How it's actually stored on secondary storage
  • Logical Name: Variable name in program (e.g., myfile)
  • Physical Name: Actual filename (e.g., data.txt)
🧠 MUST MEMORIZE: Main memory is ~100,000 times faster than secondary storage, but is volatile and expensive. Files provide persistent, large-capacity storage.

📐 Field Organization Methods

Method Description Advantages Disadvantages
Fixed Length Each field has predetermined size Easy to read/store, direct access possible Wastes space with padding
Length Indicator Size prefix before each field Easy to jump to end of field Long fields need >1 byte (max 255)
Delimited Special character separates fields May waste less space Must check every byte
Keyword=Value Self-describing fields Allows missing fields Wastes space with keywords

✅ Section 1 Final Exam Checklist

  • Define: File, Record, Field, Primary Key, Secondary Key
  • Explain difference between logical and physical files
  • Compare four field organization methods with advantages/disadvantages
  • Know when to use each organization method

2. Fundamental File Operations

🔥 HIGH EXAM WEIGHT: Seek operations and File Modes appear in EVERY exam!

📌 File Modes in C#

Mode File Exists File Doesn't Exist

📐 Seek Operations - EXAM CRITICAL

🧠 MUST MEMORIZE - Seek Syntax

long Seek(long newPos, SeekOrigin origin)
  • SeekOrigin.Begin - From start of file (position 0)
  • SeekOrigin.Current - From current position
  • SeekOrigin.End - From end of file
⚠️ COMMON EXAM TRICK: When seeking from End, use NEGATIVE values to go backward. Positive values from End are invalid for reading!
❌ COMMON MISTAKE: Students forget that SeekOrigin.End requires negative offset to read backward from end.

✍️ Exam-Style Worked Example

Example: Seek Operations on a 100-byte File

Given: File size = 100 bytes, Current position = 30

1. myfile.Seek(10, SeekOrigin.Begin);
Result: Position = 10 (moves to byte 10 from start)
2. myfile.Seek(5, SeekOrigin.End);
Result: Position = 105 (beyond file end - valid for writing, invalid for reading!)
3. myfile.Seek(-10, SeekOrigin.Current);
From position 30: Result = 30 - 10 = 20
4. myfile.Seek(-10, SeekOrigin.End);
Result: Position = 100 - 10 = 90 (correct way to seek from end!)

3. Reclaiming Space in Files (AVAIL LIST)

🔥 HIGH EXAM WEIGHT: AVAIL LIST questions appear on EVERY final exam. This is 10-15 marks guaranteed!

📌 Core Concepts

AVAIL LIST (Available List)

  • A linked list (stack structure) of deleted records
  • Header record stores the list head (position of first available record)
  • List head = -1 means empty list (no deleted records)
  • Each deleted record stores: *NextPointer|Size
  • Implemented as a stack: Last deleted = First reused (LIFO)

Fragmentation Types

  • Internal Fragmentation: Wasted space WITHIN a record (new record smaller than deleted space)
  • External Fragmentation: Space in AVAIL LIST too small to reuse
🧠 MUST MEMORIZE: AVAIL LIST operations: DELETE = Push to stack, ADD = Pop from stack (if size fits)

📐 Placement Strategies - EXAM RULE

Strategy AVAIL LIST Order Selection Rule Best For
First-Fit Unsorted First record large enough Minimizing search time
Best-Fit Ascending by size Smallest record that fits Minimizing internal fragmentation
Worst-Fit Descending by size Largest available record Minimizing external fragmentation (leftover returned to list)
⚠️ EXAM RULE: First-Fit minimizes search through AVAIL LIST (stops at first match). Best-Fit and Worst-Fit require checking entire list!
❌ COMMON MISTAKE: Students confuse Best-Fit with Worst-Fit. Best = smallest that fits (ascending), Worst = largest (descending).

✍️ Exam-Style Worked Example

Complete Example: Worst-Fit Strategy

Given: File with records R1(size=30), R2(size=12), R3(size=50), R4(size=40), R5(size=17)

Operations: Delete R3, Add R6(20), Add R7(20), Delete R2, Add R8(10)

1️⃣ INITIAL STATE TABLE

Address Record Size Status
0 R1 30 Active
30 R2 12 Active
42 R3 50 Active
92 R4 40 Active
132 R5 17 Active

Initial Header = -1 (AVAIL LIST is empty)

2️⃣ OPERATION-BY-OPERATION TABLE

OPERATION 1: DELETE R3 (size=50)
Strategy: N/A (deletion always pushes to stack)
AVAIL LIST BEFORE: Empty (Header = -1)
Action: Push R3 to AVAIL LIST at address 42
Record Content: R3 becomes *-1|50
AVAIL LIST AFTER: Header = 42
Address Next Size
42 -1 50
OPERATION 2: ADD R6 (size=20) - WORST-FIT
Strategy: Worst-Fit (use largest available)
AVAIL LIST BEFORE: Header = 42
Address Size
42 50

- Only one block available: size=50
- R6 needs 20 bytes
- 20 ≤ 50? YES ✓ Use this block
- Leftover: 50 - 20 = 30 bytes
- Return leftover to AVAIL LIST at address 62 (42+20)
AVAIL LIST AFTER: Header = 62
Address Next Size
62 -1 30
OPERATION 3: ADD R7 (size=20) - WORST-FIT
Strategy: Worst-Fit (use largest available)
AVAIL LIST BEFORE: Header = 62
Address Size
62 30
Decision Logic:
- Only one block: size=30
- R7 needs 20 bytes
- 20 ≤ 30? YES ✓ Use this block
- Leftover: 30 - 20 = 10 bytes
- Return leftover at address 82 (62+20)
AVAIL LIST AFTER: Header = 82
Address Next Size
82 -1 10
OPERATION 4: DELETE R2 (size=12)
Strategy: N/A (deletion), then SORT for Worst-Fit
AVAIL LIST BEFORE: Header = 82
Address Size
82 10
Action: Push R2 at address 30
Before Sorting: 30(size=12) → 82(size=10)
Sort Descending: 12 > 10, so 30 comes first
AVAIL LIST AFTER: Header = 30
Address Next Size
30 82 12
82 -1 10
OPERATION 5: ADD R8 (size=10) - WORST-FIT
Strategy: Worst-Fit (use largest available)
AVAIL LIST BEFORE: Header = 30
Address Size
30 12
82 10
Decision Logic:
- Largest block: address=30, size=12
- R8 needs 10 bytes
- 10 ≤ 12? YES ✓ Use this block
- Leftover: 12 - 10 = 2 bytes
- 2 bytes too small to store header info → EXTERNAL FRAGMENTATION
- Leftover is lost (not returned to list)
AVAIL LIST AFTER: Header = 82
Address Next Size
82 -1 10

3️⃣ AVAIL LIST REPRESENTATION

Linked List Format:
Header = 82

Address: 82 → Content: *-1|10

Logical Representation:
82 [10 bytes] → -1

4️⃣ FRAGMENTATION ANALYSIS

Operation Internal Fragmentation External Fragmentation
Op 1: Delete R3 NO NO
Op 2: Add R6(20) NO (leftover returned) NO
Op 3: Add R7(20) NO (leftover returned) NO
Op 4: Delete R2 NO NO
Op 5: Add R8(10) NO (exact fit with 2-byte loss) YES - 2 bytes lost

External Fragmentation Details: 2 bytes remaining at address 40 cannot be reused (too small to store AVAIL LIST header: NextPointer + Size)

5️⃣ FINAL STATE SUMMARY

Final Header Value: 82

Final AVAIL LIST Order: 82 → -1

Remaining Reusable Blocks: [10]

Total Wasted Space: 2 bytes (external fragmentation)

6️⃣ INSTRUCTOR EXAM NOTES

🧠 GRADING KEY POINTS:
✓ Worst-Fit MUST sort in descending order after each deletion
✓ Always show leftover calculation: Original - NewRecord
✓ Return leftover to AVAIL LIST (except when too small)
✓ Address of leftover = Original Address + NewRecord Size
✓ External fragmentation occurs when leftover < header size (typically 8+ bytes needed)
✓ Final answer must show: Header value + List order + Sizes
❌ COMMON EXAM ERRORS:
• Forgetting to sort after deletion in Best/Worst-Fit
• Wrong leftover address calculation
• Not identifying external fragmentation
• Confusing "List head" with "List tail"
• Using ascending sort for Worst-Fit (should be descending!)

4. Searching & Binary Search

📌 Core Concepts

Sequential Search vs Direct Access

  • Sequential Search: Read records one by one until found
  • Time Complexity: O(n) - must check all records in worst case
  • Average: n/2 records read (for n=2000, average=1000 reads)
  • Direct Access: Jump directly to record using RRN (Relative Record Number)
  • Time Complexity: O(1) - constant time
  • Requirement: Fixed-length records only

Binary Search

  • Requirement: File must be SORTED by key
  • Method: Repeatedly divide list in half
  • Time Complexity: O(log₂n)
  • Average: 1 + log₂n records (for n=2000, average=11 reads)
  • Requirement: Fixed-length records (need RRN)
🔥 HIGH EXAM WEIGHT: Comparison of search methods and RRN calculation appear frequently!

📐 Exam Rules & Formulas

🧠 MUST MEMORIZE - RRN and Byte Offset

Byte Offset = RRN × Record Length

Example: RRN=30, Record Length=101 bytes

Byte Offset = 30 × 101 = 3030

Note: First record has RRN=0 (not 1!)

🧠 MUST MEMORIZE - Search Comparisons

Method Time Complexity Average Reads (n=2000) Requirements
Sequential O(n) 1000 None
Binary Search O(log₂n) 11 Sorted + Fixed-length
Direct Access (RRN) O(1) 1 Fixed-length
Hashing O(1) 1-2 Hash function
⚠️ EXAM RULE: Binary search DOUBLES file size → Only ONE additional read needed! (log₂(2n) = log₂n + 1)

✍️ Exam-Style Worked Example

Example: RRN Calculation and Direct Access

Given:
- File with fixed-length records
- Record length = 50 bytes
- Want to access record with RRN = 25
Step 1: Calculate Byte Offset
Byte Offset = RRN × Record Length
Byte Offset = 25 × 50 = 1250 bytes
Step 2: Use Seek to Access
myfile.Seek(1250, SeekOrigin.Begin);
This positions the file pointer at the start of record 25
Step 3: Read the Record
myfile.Read(buffer, 0, 50);
Reads 50 bytes (one complete record)

5. Blocking & Buffering

🔥 HIGH EXAM WEIGHT: Differences between blocking/buffering and I/O calculations are guaranteed exam questions!

📌 Core Concepts

Blocking

  • Definition: Grouping multiple records into fixed-size blocks
  • Purpose: Reduce NUMBER of I/O operations
  • Process: Read/write entire blocks instead of individual records
  • Benefit: Fewer system calls = reduced I/O overhead
  • Best for: Sequential file access, batch processing

Buffering

  • Definition: Using memory (buffers) to temporarily store data during I/O
  • Purpose: Bridge speed gap between CPU and disk
  • Process: Data moves: Disk ↔ Buffer ↔ CPU
  • Benefit: Enables overlapping of CPU and I/O operations
  • Best for: Real-time systems, streaming
🧠 MUST MEMORIZE: Blocking reduces the NUMBER of I/O operations, NOT their size. Buffering enables PARALLELISM between CPU and I/O.
❌ COMMON MISTAKE: Students confuse blocking (data organization) with buffering (memory management). They serve different purposes!

📐 Exam Rules & Formulas

🧠 MUST MEMORIZE - Blocking Formula

Number of I/O Operations = ⌈R / B⌉

Where:

  • R = Total number of records
  • B = Block size (records per block)
  • ⌈ ⌉ = Ceiling function (round up)

Example: 10,000 records, block size = 200

I/O Operations = ⌈10,000 / 200⌉ = ⌈50⌉ = 50
Feature Blocking Buffering
Focus Grouping records into blocks Temporary storage in memory
Primary Use Reducing I/O frequency Bridging speed differences
Memory Use Larger blocks Smaller buffers
Complexity Simpler to implement More complex (especially double buffering)
Example Database pages Video streaming

Single vs Double Buffering

Feature Single Buffering Double Buffering
Memory One buffer Two buffers
Performance Limited parallelism CPU and I/O overlap
Implementation Simple More complex
Idle Time CPU or I/O may wait Minimizes idle time
Use Case Small-scale systems Performance-critical systems
🧠 EXAM RULE: Double buffering allows CPU to process Buffer 1 while I/O fills Buffer 2 simultaneously = TRUE PARALLELISM.

✍️ Exam-Style Worked Example

Example: I/O Operations Calculation

Question: How many I/O operations are needed for 10,000 records with a block size of 200 records?
Step 1: Identify Values
R = 10,000 records
B = 200 records per block
Step 2: Apply Formula
Number of I/O Operations = ⌈R / B⌉
= ⌈10,000 / 200⌉
= ⌈50⌉
= 50 I/O operations
Step 3: Interpretation
Without blocking: 10,000 I/O operations (one per record)
With blocking: 50 I/O operations
Improvement: 200× reduction in I/O operations!
