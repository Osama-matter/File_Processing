CHAPTER 1

Introduction to File Organization

Foundational concepts: Files, Memory vs Disk, File Structure Types

📖 Core Concepts

💡 What is a File?

File: A collection of data placed under secondary or non-volatile storage (e.g., hard drive, SSD, tape). Files persist after power loss, unlike RAM.

Data Structures vs File Structures

Aspect Data Structures File Structures
Location Main memory (RAM) Secondary storage (disk)
Speed Fast (~120 nanoseconds) Slow (~30 milliseconds)
Speed Ratio RAM is ~100,000× faster than disk
Persistence Volatile (lost on power off) Non-volatile (persistent)
Size Small, expensive Large, cheap
🎓 Instructor Tip: Memory the Speed Analogy

Students often forget the magnitude of speed difference. Use this analogy in exams:

  • Looking at book index: 20 seconds (RAM)
  • Going to library: 54 days (Disk)

This 100,000× ratio is why we minimize disk I/O operations in every topic (blocking, buffering, indexing, hashing).

File Structure Types

Logical Structure

How programmers see the file

  • Text files (.txt, .csv)
  • Image files (.jpg, .png)
  • Data files (.db, .dat)
  • Document files (.docx, .pdf)
Physical Structure

How file is stored on disk

  • Tracks and sectors
  • Blocks (clusters)
  • Cylinders
  • Physical addresses

File Organization Goals

  1. Fast Access Time: Minimize disk trips (each trip = ~30ms overhead)
  2. Good Space Utilization: Reduce wasted space (fragmentation)
  3. Efficient Data Retrieval: Get what you need in one access

File Operations & C# Programming

FileMode, FileAccess, Seek Operations — Question 1 Focus

📖 Core Concepts

💡 Physical vs Logical Files

Physical File: Collection of bytes on disk, known by operating system, appears in file directory

Logical File: Channel/object in program (FileStream, StreamReader) that links to physical file

C# — Opening Files FileStream myFile = new FileStream("sample.txt", FileMode.Open, FileAccess.Read); StreamReader reader = new StreamReader(myFile); // Later: Close to free resources reader.Close(); myFile.Close();

File Modes — MEMORIZE THIS TABLE

⚡ This Appears in Question 1 Every Year

You must memorize all 6 modes and their exact behaviors when file exists vs doesn't exist.

Mode Description File Exists? File Doesn't Exist?
Open Opens existing file ✅ Opens ❌ Error (Exception)
Create Creates new file ⚠️ Deletes & recreates ✅ Creates new
CreateNew Creates only if doesn't exist ❌ Error (Exception) ✅ Creates new
Append Adds to end of file ✅ Opens, adds to end ✅ Creates & adds
Truncate Deletes all contents ✅ Opens, empties file ❌ Error (Exception)
OpenOrCreate Opens or creates ✅ Opens ✅ Creates
❌ Common Mistake: Create vs CreateNew

Students confuse these two:

  • Create: Always succeeds. If file exists, it deletes it first (DATA LOSS!).
  • CreateNew: Safe mode. If file exists, throws error (prevents accidental overwrite).

Exam Trap: "Which mode prevents data loss if file exists?" → Answer: CreateNew

File Access Types

Access Mode Can Read? Can Write? Common Use
FileAccess.Read ✅ Yes ❌ No Reading log files, viewing data
FileAccess.Write ❌ No ✅ Yes Writing output, creating new files
FileAccess.ReadWrite ✅ Yes ✅ Yes Database files, random access

🎯 Seek Operations (HIGH EXAM PROBABILITY)

⚡ Question 1 ALWAYS Includes Seek Questions

You will get 2-3 Seek questions worth 3-5 points. Master this syntax and all three origins.

💡 Seek Syntax
myfile.Seek(offset, SeekOrigin); // Returns: new position in file (long)

SeekOrigin Values

Origin Starting Point Positive Offset Negative Offset
SeekOrigin.Begin Start of file (byte 0) Move forward from start ❌ Invalid (can't go before start)
SeekOrigin.Current Current file position Move forward ✅ Move backward
SeekOrigin.End End of file Move beyond end (for writing) ✅ Move backward from end

Worked Examples — Step by Step

📝 Example 1: Basic Seek Operations

File size: 100 bytes. Current position: byte 50.

1
myfile.Seek(10, SeekOrigin.Begin);
Position = 0 + 10 = 10
→ Moves to byte 10 from start
2
myfile.Seek(-10, SeekOrigin.Current);
Position = 50 + (-10) = 40
→ Moves 10 bytes backward from current position
3
myfile.Seek(0, SeekOrigin.End);
Position = 100 + 0 = 100
→ Moves to last byte (position 100)
4
myfile.Seek(-20, SeekOrigin.End);
Position = 100 + (-20) = 80
→ Moves to byte 80 (20 bytes before end)
❌ Common Mistake: SeekOrigin.End Confusion

Students think: Seek(5, SeekOrigin.End) moves to byte 5 from end.

Reality: It moves 5 bytes AFTER the end (position 105 in 100-byte file).

To move 5 bytes before end: Use Seek(-5, SeekOrigin.End) → position 95

🎓 Instructor Tip: Seek Question Strategy

In exams, always:

  1. Write down file size and current position
  2. Draw a number line (0 to file size)
  3. Mark current position with arrow
  4. Calculate: Starting Point + Offset = New Position
  5. Check if position is valid (0 to file size)

Time allocation: 30 seconds per Seek question. Don't overthink it.

CHAPTER 3

Field & Record Organization

Keys, Field Organization Methods, Fixed vs Variable-Length Records

📖 Core Concepts

💡 Basic Definitions

File: Collection of records

Record: Collection of related fields (one entity)

Field: Smallest logically meaningful unit of information

Key: Field(s) used to identify/search for a record

Types of Keys

Key Type Uniqueness Purpose Examples
Primary Key Unique (1-to-1) Uniquely identifies each record Student ID, ISBN, Course Code
Secondary Key Non-unique (1-to-many) Used for searching/grouping Department, Author, City
🎓 Instructor Tip: Key Selection

Primary Key Rules:

  • Must be unique (no duplicates allowed)
  • Should never change (stable identifier)
  • Cannot be NULL

Exam Tip: If asked "Which field is the primary key?" → Choose the field that uniquely identifies each record (ID numbers, codes, not names/departments)

📝 Field Organization Methods

Method How It Works Advantages Disadvantages
1. Fixed Length Each field has predetermined size
Example: Name[20], ID[5]		 • Easy to read/write
• Fast direct access
• Simple calculations		 • Wastes space (padding)
• Inflexible (truncation if too long)
2. Length Indicator Store length before data
Example: 05AHMED		 • Easy to jump to end
• Less waste than fixed
• No delimiter conflicts		 • Max 255 bytes (1-byte length)
• Extra bytes for length field
3. Delimiters Separate fields with special character
Example: AHMED|CS|2		 • Flexible length
• Simple to implement		 • Must scan every byte
• Delimiter can't appear in data
• Slower access
4. Keyword=Value Self-describing pairs
Example: ID=123|NAME=AHMED		 • Self-documenting
• Missing fields allowed
• Flexible order		 • High space overhead
• Slower parsing
• Redundant keywords
📝 Example: Same Data in Different Formats

Data: ID=123, Name=Ahmed, Dept=CS

1
Fixed Length (5+20+3 = 28 bytes)
00123Ahmed_______________CS_
→ 28 bytes (padded with spaces/underscores)
2
Length Indicator
0500123 05Ahmed 02CS
→ 21 bytes (3 length bytes + 18 data bytes)
3
Delimiters (using |)
00123|Ahmed|CS
→ 14 bytes (2 delimiters + 12 data bytes)
4
Keyword=Value
ID=00123|NAME=Ahmed|DEPT=CS
→ 29 bytes (keywords add overhead)
🎓 Instructor Tip: When to Use Each Method

Fixed Length: Use for databases with uniform data (student records, employee IDs)

Length Indicator: Use for variable text with known max size (articles, descriptions)

Delimiters: Use for CSV files, log files, simple parsing

Keyword=Value: Use for config files, APIs, self-documenting data (JSON-like)

📝 Record Organization Types

Fixed-Length Records

All records have the same size

  • Advantage: Direct access using RRN
  • Advantage: Simple calculations
  • Advantage: Easy to update in place
  • Disadvantage: Wasted space (padding)
  • Disadvantage: Inflexible (fixed max sizes)
Variable-Length Records

Records vary in size

  • Advantage: No wasted space
  • Advantage: Flexible field sizes
  • Disadvantage: Cannot use RRN
  • Disadvantage: Need byte offsets
  • Disadvantage: Complex updates

RRN (Relative Record Number) — Fixed-Length Only

💡 RRN Concept

RRN: Logical position of record (0, 1, 2, 3...)

Only works with fixed-length records!

Byte Offset = RRN × Record Length
⚡ Common Exam Question

Problem: File has fixed-length records, 101 bytes each. Find byte offset for RRN=30.

Byte Offset = 30 × 101 = 3030 bytes

Then use: myfile.Seek(3030, SeekOrigin.Begin);

📝 Worked Example: Direct Access with RRN

Given: Student records, 150 bytes each. Find student at RRN=45.

1
Calculate byte offset
Byte Offset = 45 × 150 = 6750 bytes
2
Seek to position
myfile.Seek(6750, SeekOrigin.Begin);
3
Read 150 bytes
byte[] buffer = new byte[150];
myfile.Read(buffer, 0, 150);
→ Got the complete student record in ONE disk access!
❌ Common Mistake: RRN with Variable-Length

Wrong: "Find record at RRN=10 in variable-length file"

Why it's wrong: RRN only works when all records are the same size. With variable-length records, you don't know where RRN=10 starts without reading all previous records.

Solution for variable-length: Use indexing (Chapter 5) or sequential search

CHAPTER 4 — ⚡ CRITICAL

Reclaiming Space in Files

AVAIL LIST, Placement Strategies, Fragmentation — Question 2 Focus (10 Points)

⚡ HIGHEST EXAM WEIGHT — 10+ Points

This chapter appears in:

  • Question 2: Full question (10 points) on placement strategies
  • Question 5: Index management with deletions (partial)

Study Time Recommendation: Spend 60-90 minutes on this chapter. It's the difference between 60% and 85%.

📖 Core Concepts

💡 Why Reclaim Space?

When records are deleted, they leave "holes" in the file. Without space reclamation:

  • File grows unnecessarily (wasted disk space)
  • New records always appended to end (even if space available)
  • Need to rebuild entire file periodically (expensive)

Solution: Maintain a list of deleted record locations (AVAIL LIST) and reuse them.

Deletion Strategies

Strategy How It Works Advantages Disadvantages
1. Record Deletion & Compaction Mark record as deleted (e.g., '*' at beginning). Later, run compaction to squeeze file. Simple to implement Wasted space until compaction. Compaction is expensive (rebuilds entire file).
2. Dynamic Reclamation (AVAIL LIST) Maintain linked list of deleted records. Reuse space immediately when adding records. Immediate space reuse. No compaction needed. Efficient. Slightly more complex. May cause fragmentation.
💡 AVAIL LIST (Linked List of Free Space)

AVAIL LIST: A stack-based linked list of available (deleted) records

  • Header record: Stores the RRN/address of first available record (-1 = empty list)
  • Deleted record format: Contains pointer to next deleted record
  • Stack behavior: Last deleted is first reused (LIFO)

🎯 Placement Strategies (MEMORIZE)

⚡ Question 2 Core Topic

You will be asked to:

  1. Explain all three strategies
  2. Compare them (which minimizes fragmentation?)
  3. Apply one strategy to a given file + AVAIL LIST
Strategy Selection Method List Sorting Speed Fragmentation
First-Fit First record large enough Not sorted (insertion order) Fastest High internal fragmentation
Best-Fit Smallest record that fits Ascending by size Medium Low internal / High external
Worst-Fit Largest record available Descending by size Medium High internal / Low external
🎓 Instructor Tip: Understanding the Trade-offs

First-Fit: Grabs first available space → Fast but wasteful

Best-Fit: Finds perfect fit → Minimizes internal waste but creates tiny unusable fragments

Worst-Fit: Uses largest space → Leaves larger reusable fragments but wastes space inside

Exam Tip: "Which minimizes search time?" → First-Fit (doesn't need sorting)

Fragmentation Types

Internal Fragmentation

Location: Inside allocated records

Cause: Record size < Available space size

  • Example: Record needs 20 bytes, space has 29 bytes → 9 bytes wasted
  • Best-Fit minimizes this
External Fragmentation

Location: Between records (in AVAIL LIST)

Cause: Leftover space too small to reuse

  • Example: After using 20 bytes from 29-byte space, 9 bytes remain (too small for any record)
  • Worst-Fit minimizes this

📝 Fixed-Length Records: AVAIL LIST Operations

💡 Format in Deleted Record

Deleted record contains: *NextRRN

  • *: Deletion marker
  • NextRRN: RRN of next deleted record (-1 = no next)
📝 Worked Example: Fixed-Length AVAIL LIST

Initial File: A (RRN=0), B (RRN=1), C (RRN=2), D (RRN=3), E (RRN=4)
Header (AVAIL): -1 (list empty)

1
Delete RRN=2 (record C)
File: A, B, *-1, D, E
Header → 2 (first available)
→ Record C marked as deleted, points to -1 (end of list)
2
Delete RRN=4 (record E)
File: A, B, *-1, D, *2
Header → 4 (new top of stack)
→ Record E marked, points to 2 (previous top). Stack: 4 → 2 → -1
3
Add new record F (First-Fit)
1. Get top of AVAIL: RRN=4
2. Place F at RRN=4
3. Update header to next: Header → 2
File: A, B, *-1, D, F
→ F reuses RRN=4. Stack now: 2 → -1
4
Add new record G (First-Fit)
1. Get top of AVAIL: RRN=2
2. Place G at RRN=2
3. Update header to next: Header → -1
File: A, B, G, D, F
→ G reuses RRN=2. AVAIL LIST now empty (-1)
5
Add new record H (list empty)
1. AVAIL = -1 (empty)
2. Append H to end
File: A, B, G, D, F, H
Header → -1 (still empty)
→ No space available, append to end at RRN=5
🎓 Instructor Tip: Drawing the Stack

In exams, always draw the linked list visually:

Header → 4 → 2 → -1 This shows: - Header points to RRN=4 - RRN=4 points to RRN=2 - RRN=2 points to -1 (end)

Common Error: Students forget to update the header when reusing space.

📝 Variable-Length Records: AVAIL LIST with Sizes

💡 Format in Deleted Record

Deleted record contains: *NextAddress|Size|

  • *: Deletion marker
  • NextAddress: Byte offset of next deleted record (-1 = no next)
  • Size: Size of this deleted record in bytes
⚡ Exam Question Pattern

Typical Question: Given file with records and AVAIL LIST, apply Best-Fit strategy to add new records.

What you must show:

  1. Initial AVAIL LIST (sorted by size for Best-Fit)
  2. For each insertion: which space is chosen, why
  3. Handle leftover space (internal fragmentation)
  4. Update AVAIL LIST after each operation
  5. Final AVAIL LIST state
📝 Worked Example: Variable-Length with Placement Strategies

Initial AVAIL LIST: size=60 (addr=100), size=50 (addr=200), size=22 (addr=300), size=10 (addr=400)

1
Strategy: First-Fit | Add record: size=20
First-Fit: Not sorted, pick first that fits
AVAIL: 60, 50, 22, 10
→ First that fits: size=60 ✓
→ Place record at addr=100
→ Internal fragmentation: 60-20 = 40 bytes wasted
→ AVAIL after: 50, 22, 10
2
Strategy: Best-Fit | Add record: size=20
Best-Fit: Sort ascending by size
AVAIL sorted: 10, 22, 50, 60
→ Smallest that fits: size=22 ✓
→ Place record at addr=300
→ Internal fragmentation: 22-20 = 2 bytes wasted
→ AVAIL after: 10, 50, 60
3
Strategy: Worst-Fit | Add record: size=20
Worst-Fit: Sort descending by size
AVAIL sorted: 60, 50, 22, 10
→ Largest: size=60 ✓
→ Place record at addr=100
→ Leftover: 60-20 = 40 bytes (large enough to reuse!)
→ Add leftover back to AVAIL: size=40 at addr=120
→ AVAIL after: 50, 40, 22, 10
❌ Common Mistake: Forgetting Leftover Space

Wrong approach: Use space, remove from AVAIL, done.

Correct approach: If leftover ≥ minimum record size (usually 10-20 bytes), add it back to AVAIL LIST!

Example: Use 20 bytes from 60-byte space → 40 bytes left → Add (addr=original+20, size=40) to AVAIL

🎓 Instructor Tip: Exam Strategy for Question 2

Time allocation: 15-20 minutes

  1. (2 min) Read question, identify which strategy to use
  2. (3 min) Draw initial file and AVAIL LIST with addresses and sizes
  3. (8 min) Step through each operation:
    • For deletion: Mark record, add to AVAIL (stack)
    • For insertion: Find space using strategy, place record, handle leftover
  4. (3 min) Draw final AVAIL LIST
  5. (2 min) Double-check: Did I sort correctly? Did I handle leftover space?

Marking scheme: Typically 3 points for process, 3 points for final AVAIL LIST, 2 points for explanation, 2 points for correct strategy application.

CHAPTER 5 — ⚡ CRITICAL

Binary Search & Indexing

Search Algorithms, Index Types, Multi-Index Queries — Question 5 Focus (15 Points)

⚡ HIGH EXAM WEIGHT — 15 Points

Question 5 (Most Complex): Design indexing system, maintain indexes through operations, answer complex queries

Skills Tested: Index creation, insertion, deletion, multi-index queries (logical AND)

📖 Sequential vs Binary Search

Aspect Sequential Search Binary Search
Time Complexity O(n) O(log₂ n)
Average Accesses n/2 records 1 + log₂ n records
For 2000 records ~1000 accesses ~11 accesses
For 1,000,000 records ~500,000 accesses ~20 accesses
Requirement No sorting needed File MUST be sorted
Record Type Any (fixed or variable) Fixed-length only
Use Case Small files, unsorted data Large files, frequent searches
🎓 Instructor Tip: The Power of Binary Search

Why binary search is revolutionary: Each comparison eliminates HALF the remaining data.

Example: 1 million records

  • Sequential: 500,000 reads on average = ~15 seconds at 30ms per read
  • Binary: 20 reads = 0.6 seconds
  • 25× faster!

The catch: File must be sorted by search key AND fixed-length records (need RRN).

📝 Binary Search Algorithm

Search for key=45 in sorted file with RRN 0-15

1
Initialize: low=0, high=15
mid = (0 + 15) / 2 = 7
Read RRN=7, key=50
→ 45 < 50, search left half
2
Update: low=0, high=6
mid = (0 + 6) / 2 = 3
Read RRN=3, key=30
→ 45 > 30, search right half
3
Update: low=4, high=6
mid = (4 + 6) / 2 = 5
Read RRN=5, key=45
→ FOUND! Only 3 disk accesses.

🎯 Indexing Concepts

💡 What is an Index?

Index: A separate file containing (key, reference) pairs that point to data records

Reference: Can be RRN (fixed-length) or byte offset (variable-length)

Why Use Indexes?

Without Index
  • Must sort entire file to use binary search
  • Sorting large files is expensive
  • Only one search order (by primary key)
  • Variable-length records can't use binary search
With Index
  • Sort small index, not large data file
  • Multiple indexes = multiple search paths
  • Works with variable-length records
  • Index fits in RAM = fast binary search
⚡ Key Advantage: Small Index Size

Example: 10,000 student records

  • Data file: 10,000 × 200 bytes = 2 MB
  • Index file: 10,000 × 10 bytes = 100 KB
  • Ratio: Index is 20× smaller!

→ Index fits in RAM, binary search on 100 KB is INSTANT

Index Types

Type Built On Uniqueness Structure Example
Primary Index Primary key field Unique (1-to-1) (Key → Address) ISBN → Book location
Secondary Index Secondary key field Non-unique (1-to-many) (Key → List of addresses) Author → List of books
📝 Example: Student Database Indexes

Data File: Student records with ID, Name, Dept, Year

1
Primary Index: Student ID
ID=1001 → RRN=0
ID=1002 → RRN=5
ID=1003 → RRN=2
(Sorted by ID for binary search)
→ Unique mapping: one ID = one record
2
Secondary Index: Department
CS → [RRN=0, RRN=2, RRN=7]
Math → [RRN=1, RRN=5]
Physics → [RRN=3, RRN=4, RRN=6]
→ Non-unique: one dept = many students
3
Secondary Index: Year
1 → [RRN=0, RRN=3]
2 → [RRN=1, RRN=4, RRN=5]
3 → [RRN=2, RRN=6, RRN=7]
→ Non-unique: one year = many students

📝 Index Operations (Question 5 Core)

⚡ These Operations Appear in Every Question 5

You must know how to perform each operation on both primary and secondary indexes.

Operation Steps Impact on Index
1. Create Initialize empty index and data files Both files created, empty
2. Load Read index from disk into memory (RAM) Index in RAM for fast searches
3. Add (Insert) 1. Append record to data file
2. Insert (key, address) into index (sorted)		 Index grows by 1 entry, stays sorted
4. Delete 1. Mark record as deleted in data file
2. Remove entry from index		 Index shrinks, data file has hole
5. Update 1. Modify record in data file
2. If key changed: delete old, insert new entry		 Index updated if key field changed
6. Rewrite Write index from memory back to disk Persist changes to disk
🎓 Instructor Tip: Critical Index Rules

Rule 1: Index must ALWAYS stay sorted by key (for binary search)

Rule 2: When adding, insert in correct sorted position (not append!)

Rule 3: When deleting, remove from index but mark (don't remove) in data file

Rule 4: If updating key field, treat as delete + add

Rule 5: Always Load → Modify → Rewrite

📝 Worked Example: Index Operations

Initial Primary Index (CourseCode → RRN):
101→0, 205→1, 323→2, 410→3

1
Add: Course 250, new record at RRN=4
1. Append record to data file at RRN=4
2. Insert (250, 4) in sorted position
Index: 101→0, 205→1, 250→4, 323→2, 410→3
→ Inserted between 205 and 323 (sorted order)
2
Delete: Course 205
1. Mark RRN=1 as deleted in data file (*)
2. Remove (205, 1) from index
Index: 101→0, 250→4, 323→2, 410→3
→ Entry removed from index, hole in data file
3
Update: Change Course 323 to 350
1. Update record at RRN=2 in data file
2. Delete (323, 2), Insert (350, 2)
Index: 101→0, 250→4, 350→2, 410→3
→ Key changed, so index entry updated

🎯 Multi-Index Queries (CRITICAL)

⚡ Question 5 Always Includes This

Task: Use multiple secondary indexes to answer complex queries with AND conditions

Example: "Find all second-year CS students in first semester"

💡 Multi-Index Query Process
  1. Search each relevant secondary index → Get list of RRNs
  2. Perform logical AND: Find RRNs that appear in ALL lists
  3. Use result RRNs to fetch actual records
📝 Worked Example: Complex Query

Query: Find all Year=2, Dept=CS, Semester=1 students

1
Search Year Index for "2"
Year=2 → [RRN: 1, 3, 5, 7, 9]
→ List A = {1, 3, 5, 7, 9}
2
Search Dept Index for "CS"
Dept=CS → [RRN: 2, 3, 5, 8, 9]
→ List B = {2, 3, 5, 8, 9}
3
Search Semester Index for "1"
Semester=1 → [RRN: 1, 3, 4, 5, 6]
→ List C = {1, 3, 4, 5, 6}
4
Logical AND: A ∩ B ∩ C
A = {1, 3, 5, 7, 9}
B = {2, 3, 5, 8, 9}
C = {1, 3, 4, 5, 6}
A ∩ B = {3, 5, 9}
(A ∩ B) ∩ C = {3, 5}
→ Final Result: RRN=3 and RRN=5
5
Fetch Records
Read record at RRN=3
Read record at RRN=5
→ Got matching students with only 2 disk accesses!
🎓 Instructor Tip: Set Intersection Strategy

In exams, show your work clearly:

  1. Write each list as a set: {1, 3, 5, 7}
  2. Do intersections step by step (don't jump to final answer)
  3. Use set notation: A ∩ B, then result ∩ C

Common mistake: Students forget one of the conditions. Triple-check you used ALL indexes mentioned in the query.

CHAPTER 6

Blocking & Buffering

I/O Optimization, Single vs Double Buffering — Question 3 Focus

📖 Core Concepts

💡 Why Blocking & Buffering?

Problem: Disk I/O is ~100,000× slower than RAM. Each disk access = ~30ms overhead.

Solution: Minimize number of I/O operations by reading/writing in larger chunks.

Blocking

Group multiple records into fixed-size blocks

  • Focus: Reducing I/O frequency
  • Method: Read/write many records at once
  • Example: Read 100 records in 1 I/O instead of 100 I/Os
Buffering

Use memory as intermediary between CPU and disk

  • Focus: Overlapping CPU and I/O operations
  • Method: Temporary storage in RAM
  • Example: CPU processes buffer 1 while I/O loads buffer 2

📝 Blocking

⚡ Common Exam Question

Given: Number of records, block size

Calculate: Number of I/O operations needed

Number of I/O Operations = ⌈Records / Block Size⌉
📝 Worked Examples
1
Example 1: 10,000 records, block size = 200
I/O Operations = ⌈10,000 / 200⌉ = ⌈50⌉ = 50
→ Only 50 I/O operations instead of 10,000!
2
Example 2: 8,500 records, block size = 100
I/O Operations = ⌈8,500 / 100⌉ = ⌈85⌉ = 85
→ 85 I/O operations (last block partially filled)
3
Example 3: 950 records, block size = 100
I/O Operations = ⌈950 / 100⌉ = ⌈9.5⌉ = 10
→ 10 operations (last block has 50 records)
Aspect Advantages Disadvantages
Blocking • Reduces I/O overhead dramatically
• Efficient for sequential access
• Better disk utilization		 • Uses more memory
• Latency for small operations
• May read unneeded records
🎓 Instructor Tip: Ceiling Function

Always use ceiling (round up):

  • 8,500 / 100 = 85.0 → Round up to 85
  • 950 / 100 = 9.5 → Round up to 10 (need one more I/O for remaining 50 records)

Why? Even if last block is partially filled, you still need one I/O to read/write it.

📝 Buffering Types

Feature Single Buffering Double Buffering
Memory Buffers One buffer Two buffers
Operation Sequential: I/O fills buffer → CPU processes → Repeat Parallel: I/O fills buffer 1 while CPU processes buffer 2
Parallelism Limited (CPU or I/O idle) High (overlaps CPU and I/O)
Idle Time CPU waits during I/O, I/O waits during processing Minimized (both work simultaneously)
Complexity Simple to implement More complex (buffer swapping)
Performance Moderate High (near 2× faster for I/O-heavy tasks)
Use Case Small-scale systems, simple applications Real-time systems, databases, high-performance apps
⚡ Common True/False Questions
TRUE: Double buffering requires two buffers, allowing overlap between CPU and I/O.
TRUE: Double buffering minimizes idle time by overlapping operations.
FALSE: Single buffering is more complex than double buffering.
→ Correction: Single buffering is SIMPLER than double buffering.
FALSE: Blocking minimizes I/O overhead by grouping records into smaller chunks.
→ Correction: Blocking groups records into LARGER chunks, not smaller.
📝 Visual Comparison: Timing Diagrams

Process 3 blocks: I/O time = 30ms, CPU time = 20ms

1
Single Buffering
Block 1: I/O(30ms) → CPU(20ms) = 50ms
Block 2: I/O(30ms) → CPU(20ms) = 50ms
Block 3: I/O(30ms) → CPU(20ms) = 50ms
Total: 150ms
→ Sequential: operations don't overlap
2
Double Buffering
Time 0-30ms: I/O loads Buffer1
Time 30-50ms: CPU processes Buffer1 | I/O loads Buffer2 (overlap!)
Time 50-70ms: CPU processes Buffer2 | I/O loads Buffer3 (overlap!)
Time 70-90ms: CPU processes Buffer3
Total: 90ms
→ 1.67× faster due to overlapping!
🎓 Instructor Tip: Understanding Overlap

Key insight: While CPU processes buffer 1, I/O system loads buffer 2. This parallelism is impossible with single buffering.

Real-world analogy:

  • Single buffer: Read page 1, think about it, then read page 2 (sequential)
  • Double buffer: While thinking about page 1, friend already fetches page 2 (parallel)

Disk Storage (HDD vs SSD)

Physical Organization, Capacity Calculations, Performance Comparison

📖 Hard Disk Drive (HDD) Components

💡 HDD Physical Organization

Platter: Circular magnetic disk where data is stored

Track: Concentric circle on platter surface

Sector: Smallest addressable unit (typically 512 bytes)

Cylinder: Set of tracks at same position on all platters

Cluster: Fixed number of contiguous sectors

Extent: Group of contiguous clusters

⚡ Capacity Formulas — MEMORIZE
Track Capacity = Sectors per Track × Bytes per Sector
Cylinder Capacity = Number of Surfaces × Track Capacity
Disk Capacity = Number of Cylinders × Cylinder Capacity
📝 Worked Example: Disk Capacity Calculation

Given: 80 cylinders, 2 surfaces, 100 sectors/track, 512 bytes/sector

1
Calculate Track Capacity
Track Capacity = 100 sectors × 512 bytes
= 51,200 bytes = 50 KB
2
Calculate Cylinder Capacity
Cylinder Capacity = 2 surfaces × 50 KB
= 100 KB
3
Calculate Total Disk Capacity
Disk Capacity = 80 cylinders × 100 KB
= 8,000 KB ≈ 7.8 MB
→ Total capacity: 7.8 MB

HDD Access Time Components

Component Description Typical Time
Seek Time Move read/write head to correct cylinder 3-15 ms (average ~9 ms)
Rotational Latency Wait for sector to rotate under head 2-8 ms (average ~4 ms)
Transfer Time Time to read/write data 0.1-1 ms (depends on size)
Total Access Time = Seek Time + Rotational Latency + Transfer Time

Hashing

Hash Functions, Collision Resolution, Search Length — Question 4 Focus (15 Points)

⚡ HIGHEST EXAM WEIGHT — 15 Points

Question 4: Hash function calculation, progressive overflow, search length

Most Technical Question: Requires arithmetic, algorithm tracing, table drawing

📖 Core Concepts

💡 Hashing Definitions

Hash Function h(k): Transforms a key into an address

Home Address: The address computed by hash function for a key

Collision: Two different keys hash to the same address

Synonyms: Keys that hash to the same address

Bucket: Logical storage unit for records with same hash value

Why Hashing? Time Complexity Comparison

Method Time Complexity For 1M Records
Sequential Search O(n) ~500,000 accesses
Binary Search (Index) O(log₂ n) ~20 accesses
B+ Tree O(log_k n) ~4 accesses (k=256)
Hashing (ideal) O(1) 1 access!
🎓 Instructor Tip: The Power of O(1)

Hashing is the ONLY method that achieves constant time lookup!

With perfect hash function (no collisions):

  • 1 record → 1 access
  • 1,000,000 records → 1 access
  • 1,000,000,000 records → 1 access

Reality: Collisions happen, so average = 2-4 accesses (still excellent!)

📝 Hash Function Examples

⚡ Common Exam Hash Function
int hash(string key) { int h = 2*key[0] + 3*key[1] + 6*key[2]; return (h mod TableSize); }

You'll be given ASCII values and asked to calculate h(key) for different keys.

1
Calculate h("Owl")

= (158 + 357 + 648) mod 13
= 1163 mod 13
= 6
→ "Owl" hashes to address 6
2

h("Low") = (2×76 + 3×111 + 6×119) mod 13
= (152 + 333 + 714) mod 13

3

❌ Common Mistakes in Hash Calculation
  1. Forgetting parentheses: Calculate sum FIRST, then mod (not mod each term)
  2. Wrong ASCII: 'A'=65, 'a'=97 (different!). Always check given table.
  3. Arithmetic errors: Double-check multiplication and addition
  4. Mod confusion: 1163 mod 13 = 1163 - (89×13) = 1163 - 1157 = 6

Property Why Important How to Achieve

Fast Computation Don't negate O(1) benefit Simple arithmetic operations

🎯 Collision Resolution: Progressive Overflow

💡 Progressive Overflow Algorithm

Insertion:

  1. Calculate home address: h(key)
  2. If address is free, place key there
  3. If occupied, try next address (h(key)+1)
  4. Wrap around: if reach end, go to address 0
  5. Continue until empty slot found

Search:

  1. Go to home address h(key)
  2. If key found → SUCCESS
  3. If empty slot → KEY NOT IN TABLE
  4. Otherwise, try next address
  5. Stop when: found, empty, or back at start
